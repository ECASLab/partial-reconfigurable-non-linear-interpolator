# PWL DFX PYNQ App

This folder contains a PYNQ host application for the `scripts`-based PWL DFX hardware flow.

The application targets the reconfigurable modules generated by the DFX design:

- `exp`
- `sigmoid`
- `exp_f16`
- `sigmoid_f16`

It uses the static shell MMIO map created by `scripts/pwl_dfx/pwl_dfx_bd_flow.tcl`:

- reset GPIO: `0x80000000`
- shutdown GPIO: `0x80010000`
  channel 1 bit 0 = shutdown request output
  channel 2 bit 0 = shutdown status input
  channel 2 bits 31:1 = last partial-reconfiguration latency in PL clock cycles
- active RP AXI-Lite control: `0x80020000`

## Files

- `app/main.py`: PYNQ application that loads the full overlay, repeatedly performs partial reconfiguration, validates the PWL outputs against software references, and can sample power during reconfiguration and operation.
- `Makefile`: stages the application and copies the full and partial bitstreams into the root-level `deliverables/` folder.

The runtime application uses the full `.hwh` metadata when loading the static design through `Overlay`. It still uses fixed MMIO addresses for reset, shutdown, and kernel control. Because the exported HWH includes a PYNQ-incompatible `rp_s_axi_control` memory-map entry, the application sanitizes a temporary copy of the HWH at runtime before loading the full bitstream.

## Usage

From the repository root:

```bash
make -C SW/pwl_dfx_pynq build
make -C SW/pwl_dfx_pynq deliver
```

This creates the root-level deliverables folder:

```text
deliverables/sw_pynq_pwl_dfx
```

The deliverables include:

- `pwl_dfx_pynq.py`
- `pwl_dfx_full_region_u_rp_rm_exp.bit`
- `pwl_dfx_full_region_u_rp_rm_exp.hwh`
- `pwl_dfx_full_region_u_rp_rm_sigmoid.bit`
- `pwl_dfx_full_region_u_rp_rm_sigmoid.hwh`
- `pwl_dfx_full_region_u_rp_rm_exp_f16.bit`
- `pwl_dfx_full_region_u_rp_rm_exp_f16.hwh`
- `pwl_dfx_full_region_u_rp_rm_sigmoid_f16.bit`
- `pwl_dfx_full_region_u_rp_rm_sigmoid_f16.hwh`
- `pwl_dfx_partial_region_u_rp_rm_exp.bit`
- `pwl_dfx_partial_region_u_rp_rm_sigmoid.bit`
- `pwl_dfx_partial_region_u_rp_rm_exp_f16.bit`
- `pwl_dfx_partial_region_u_rp_rm_sigmoid_f16.bit`

Example execution on the target board:

```bash
python3 pwl_dfx_pynq.py
python3 pwl_dfx_pynq.py --run sigmoid
python3 pwl_dfx_pynq.py --full-rm sigmoid --run both
python3 pwl_dfx_pynq.py --full-rm exp_f16 --run both
python3 pwl_dfx_pynq.py --run exp_f16,sigmoid_f16
python3 pwl_dfx_pynq.py --run exp --iterations 20
python3 pwl_dfx_pynq.py --run exp --iterations 20 --power-rail hwmon:ina260_u14:power1_input
python3 pwl_dfx_pynq.py --run exp_f16 --partial-bit exp_f16=/home/xilinx/exp_f16_partial.bit
python3 pwl_dfx_pynq.py --summary-file /home/xilinx/jupyter_notebooks/pwl_dfx_run.txt
python3 pwl_dfx_pynq.py --list-rails
python3 pwl_dfx_pynq.py --run sigmoid --debug
python3 pwl_dfx_pynq.py --full-programmer fpga_manager --debug
```

Use `--debug` to print progress through:

- full bitstream download
- MMIO mapping
- shutdown/reset handshakes
- partial bitstream download
- buffer sync
- kernel start and completion polling

`--iterations N` repeats each requested RM `N` times. Every iteration always performs a partial reconfiguration first, even if the target RM matches the RM that was already active.

`--run both` selects the full-RM precision pair:

- `--full-rm exp` runs `exp` then `sigmoid`
- `--full-rm exp_f16` runs `exp_f16` then `sigmoid_f16`

Use `--run all` to iterate across every supported RM, or pass a comma-separated list such as `--run exp,sigmoid_f16`.

At the end of each run, the app writes the final summary lines to `pwl_dfx_pynq_summary.txt` next to the script by default. Use `--summary-file` to choose a different output path.

## Power Measurement

The DFX app splits power measurement into two stages per iteration:

- reconfiguration:
  idle before partial reconfiguration, then active sampling while the RP is shut down, reconfigured, and resumed
- operation:
  optional stabilization delay after reconfiguration, idle sampling again, then active sampling while the RM kernel runs

At the end of all iterations for each RM, the app prints average idle, active, and delta power for:

- reconfiguration
- operation

For operation, it also reports comparable timing metrics across implementations:

- `avg_active_window_ms`
- `avg_kernel_ms`
- `avg_validation_ms`
- `avg_host_overhead_ms`

It also reports average DFX latency in PL clock cycles.

If `pynq.get_rails()` is empty on the board, the app falls back to Linux `hwmon` power sources such as `hwmon:ina260_u14:power1_input`. Use `--list-rails` to inspect what the image exposes.

Use `--full-programmer fpga_manager` if the standard `Overlay` path still fails while parsing the full-design metadata. In that mode the app programs the full bitstream through Linux `fpga_manager` and skips full-overlay metadata parsing entirely.
